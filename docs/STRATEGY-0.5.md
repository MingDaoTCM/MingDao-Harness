### 1.2 本次新增的关键事实：下游垂域已经真实存在

`Deyi-TCM-Harness`（中医垂域层）不是玩具——它有患者主键模型（病历号）、同名不静默合并、四态对比、回访追踪、诊断字段强制保留等**真实行业约束**。它证明了一件事：

> **MingDao 的内核可以被一个受监管的垂域团队复用，做出该行业的智能体。**

这是 DSH / WorkBuddy / Claude Code 都没有的东西：它们提供的是**通用能力**，而垂域需要的是**领域约束 + 私有化 + 合规**。

### 1.3 但同时，下游暴露了上游最致命的缺口（已实测确认）

通读 `Deyi-TCM-Harness/layer/providers/dify.mjs`（286 行）后确认：**整个中医域逻辑被塞在一个 Provider 的 `chat()` 里**。原因是上游没有「垂域包」这个一等扩展点。代价是具体的：

| 损失的能力 | 证据 |
| --- | --- |
| 权限引擎 / 沙箱 | 域内 3 个「工具」是 `chat()` 里的字符串正则（`/^(回访\|随访)\s*(.*)$/`），绕过 `permissions.js` |
| 审计追溯 | 不写 `audit.jsonl`，无法回答「谁在什么时候读了哪位患者的病历」 |
| 费用与护栏 | 域内每次 DeepSeek 调用硬编码 `usage: { prompt_tokens: 0, completion_tokens: 0 }` —— **完全不计费、不触发日费用护栏** |
| UI 工具卡片 / 流式 | 只能手工 `opts.onDelta`，无工具卡片、无思考实况 |
| 独立版本与契约 | 只能整文件覆盖，无 `apiVersion`、无兼容性保证、无法 CI 验证 |
| 记忆/技能/预设复用 | 全部用不上 |

**结论：上游下一阶段最高价值的投入，不是再加一个省钱特性，而是把「垂域 Pack」变成有契约的一等公民。** 这既是产品差异化，也是上下游协同的技术前提。

## 二、格局：2026-09 的生态位与避战原则

外部事实沿用 `STRATEGY-NEXT.md` 的实查结论（DSH 官方框架 / WorkBuddy 通用平台 / Claude 企业级 / 浪潮元脑本地一体机）。在此基础上补一条本次复盘得到的新判断：

| 生态位 | 谁占了 | 他们为什么不会来抢我们的位置 |
| --- | --- | --- |
| 通用框架/插件生态 | **DSH**（官方 + Cordis + MIT） | 拼框架完备度是正面撞车，且我们零依赖的设计恰恰不能要重插件内核 |
| 通用 Agent 云平台 | **WorkBuddy**（腾讯级资源战） | 需要硬件/行业伙伴/平台治理，不可复制，也不该丢下已有垂直深度 |
| 通用 Coding Agent | Claude Code / Cursor / OpenHands | 榜单与订阅模式不是我们的战场 |
| **受监管垂域的私有化智能体内核** | **空档** | 单垂域市场天花板低、需要领域伙伴、必须私有化交付、无法标准化成云 SKU——巨头做了不划算 |

**四条避战原则（在旧三条上补第四条）：**

1. **不拼框架拼契约**——DSH 的框架深度拼不过，但「分钟级上手 + 不改内核就能定制」是 Cordis 给不了的。
2. **不拼平台拼私有**——WorkBuddy 拼云上生态，我们拼「你的模型、你的机器、你的数据不出门」。
3. **不拼通用拼垂直**——通用办公让 WorkBuddy/讯飞去卷；我们把省钱与本地模型做到他们不划算做的深度。
4. **不拼能力拼确定性**（新增，本阶段核心）——巨头都在堆「能力上限」（更强的模型、更多的工具、更大的生态）；**我们补的是「能力之外的三件确定性」**：约束必被强制、成本可预测可归因、行为可审计可回放。能力可以追平，确定性是架构选择——云平台的多租户托管模型天然给不了。

## 三、定位升级：一句话与新内核

> **旧定位（STRATEGY-NEXT）**：模型中立、零依赖、会省钱、私有化第一公民的 Agent 内核与终端。
>
> **新定位（本文）**：**可私有化的垂域智能体内核**——
> 「**低依赖、可审计、约束优先、成本可归因**」，给垂域团队一个**不 fork 内核**就能做出合规智能体的基座。

**三层产品结构（不是二选一，是同心圆）：**

```
        ┌─────────────────────────────────────────────┐
   第三层 │  垂域 Pack（中医/法律/教育/制造/政务…）        │  ← 行业伙伴 / 下游仓库
        │  领域工具 · 领域红线 · 领域提示词 · 领域记忆     │
        ├─────────────────────────────────────────────┤
   第二层 │  Pack 契约 + 约束引擎 + 归因账本（v0.5 新增）  │  ← 本仓库（护城河）
        ├─────────────────────────────────────────────┤
   第一层 │  通用内核：agent 循环 / 工具 / 权限 / 上下文    │  ← 本仓库（已建成）
        │  Provider / 会话 / 省钱 / 本地模型自适应        │
        └─────────────────────────────────────────────┘
```

- **第一层**是已有的通用能力（继续维护，不再无限加特性）；
- **第二层是本阶段的主攻**，也是「有自己特色的智能体框架」的落点；
- **第三层**由垂域伙伴/下游仓库提供，上游只提供契约与参考实现。

**产品线（Coding + DeepSeek 省钱）不变**——它是第二层的活广告与真实用户来源。比例维持 `STRATEGY-NEXT` 的「产品线 : 内核线 = 2 : 1」，但本阶段内核线的一次性投入会偏高（因为要一次性把契约做对）。

## 四、特色：三个「确定性」——我们和所有头部框架的分野

头部框架在比「能力」：模型更强、工具更多、生态更大。MingDao 不比能力上限，比**确定性下界**——这对私有化/受监管场景是采购硬指标，对通用框架是架构上给不了的东西。

### 确定性 ①：约束确定性（Constraint Certainty）——红线不靠模型自觉

**问题**：垂域的红线（「缺项绝不编造」「不输出诊疗结论」「不得跨患者串病历」）今天只能写在提示词里。提示词是建议，不是强制；模型一次越界就是医疗/法律事故。

**做法**：把领域红线做成**内核级声明式约束**，由 harness 强制执行、阻断并留痕：

```jsonc
// pack.json 片段
"constraints": [
  { "id": "no-diagnosis-conclusion", "kind": "output-forbid",
    "pattern": "有效|好转|治愈|确诊为", "action": "block-and-rewrite" },
  { "id": "ten-questions-complete", "kind": "completeness",
    "fields": ["zhushu","zhenduan","hanre","han","toushen","erbian","yinshi","xiongfu","kouke","jiubing"],
    "onMissing": "require-tool", "tool": "intake_collect" },
  { "id": "no-cross-patient", "kind": "tool-arg-require",
    "tool": "intake_read", "requireArg": "patientId", "action": "block" }
]
```

内核在三个时机强制：**PreToolUse（工具与参数）→ PostToolUse（结果）→ 输出前（正文）**，每次触发都写审计。这是提示词工程做不到的，也是通用框架不会做的（它们没有「垂域红线」这个抽象）。

### 确定性 ②：成本确定性（Cost Certainty）——预算可预测、可归因、可阻断

**问题**：私有化采购最怕「账单不可控」。今天的省钱纵深很强，但**归因粒度不够**：域内模型调用可以完全不计费（Deyi 实测 `usage: 0`），子代理消耗曾经漏计（本次审计已修）。

**做法**：
1. **统一 LLM 出口**：Pack 内所有模型调用必须走 `ctx.llm()`，自动并入 usage / 缓存命中 / 峰谷 / 护栏——域内调用再也无法「隐身」。
2. **四维归因账本**：`(pack, tool, model, session)` 四级分账，`mingdao cost report --by pack` 可导出。
3. **预算即资源**：日/周/单任务预算在 Pack 级可设，触顶按 `warn/block/downgrade` 处理（复用已有护栏）。
4. 诚实原则：无价模型必须显式告警「无法估算」，绝不显示 `¥0.0000` 冒充免费（v0.4.5 已做，继续守住）。

### 确定性 ③：行为确定性（Behavior Certainty）——每步可审计、可回放、可追责

**问题**：受监管场景要回答「这个结论是怎么来的」。今天的 `audit.jsonl` 是追加日志，能追溯但不可回放。

**做法**：
1. **执行账本**：工具调用 + 模型轮次 + 约束触发 + 权限决策 + 费用，统一为可导出的事件流（脱敏）。
2. **可回放**：给定账本 + 同一模型，可在离线环境重放一次执行路径（用于事故复盘与验收测试）。
3. **合规导出**：`mingdao audit export --since --until --format pdf/json`，一键出脱敏审计报告。
4. **离线证明**：出网白名单 + 出网事件入账，用于「数据不出门」的自证。

## 五、护城河重估（诚实版）

| # | 护城河 | 为什么难抄 | 现状 |
| --- | --- | --- | --- |
| 1 | **DeepSeek 省钱纵深链** | 官方词表黄金值 + 峰谷双窗口 + 缓存 1/30 + Batch 半价 + bench 棘轮 208 断言的组合 | 已建成，持续加深 |
| 2 | **零依赖可审计内核** | 主流框架全是依赖树；「一条命令装完 + 逐行可审计」是**等保/信创测评的硬门槛**，推倒重来才能做到 | 已建成（第二层要把它变成卖点） |
| 3 | **本地模型自适应** | 大厂绑定自家云端；「单机/内网跑长任务不中断」是空档 | 已建成，是垂域私有化的前提 |
| 4 | **垂域 Pack 契约 + 约束引擎** | 需要把「领域红线」抽象成内核原语；通用框架抽象层次不同，改不动 | **本阶段新建**（新护城河） |
| 5 | **工程可信度** | strict 0/0 + 覆盖率 + bench + 三平台 CI + 每次发布自检的纪律 | 已建成，需随版本升级配额 |

**伪护城河（警惕）**：功能/技能数量、省钱百分比数字、「先发」本身。都不构成壁垒。

**正确的用法**：靠 **#1+#2+#3+#4+#5 的组合**，而不是单点。单点都可被追平，组合 + 垂域纵深 + 节奏难被复制。

## 六、明确不做（防止战略漂移）

- ❌ 不自研模型、不做云端 Agent 平台、不做账号/订阅/抽成体系
- ❌ 不引入 Cordis / 任何重依赖插件内核（零依赖是根基，也是等保卖点）
- ❌ 不做插件商店规模竞赛（DSH / WorkBuddy 的地盘）
- ❌ 不在通用 Coding 榜单上正面竞争
- ❌ 不做硬件、不做行业应用商店抽成
- ❌ **不把任何单一垂域的业务逻辑写进内核**（内核只提供抽象；中医在 Pack 里）

## 八、上下游协同机制（MingDao ↔ Deyi）

这是本次迁移后**新增的工程约束**：上游在 macOS 本机（DSH 开发），下游在 Linux 原机继续，两条线并行。

### 8.1 边界（不变，写进契约）
- 下游**只通过扩展点接入**，绝不修改上游源码（`Deyi` README 已明确）；
- 内核 bug 在**上游修**，下游不重复造；
- 上游不把任何中医逻辑写进内核。

### 8.2 接口契约（本阶段建立）
| 项 | 上游承诺 | 下游义务 |
| --- | --- | --- |
| `apiVersion` | 同一 major 内 Pack API 向后兼容（minor 只增不改） | 在 `pack.json` 声明 `apiVersion` |
| 版本窗口 | 支持最近 2 个 minor（如 0.5/0.6） | `engines.mingdao: ">=0.5 <0.7"` |
| 兼容验证 | 提供 `mingdao pack verify` + 兼容性矩阵文档 | 把 `pack verify` 放进自己的 CI |
| 破坏性变更 | 走 major 升级 + 提供迁移指南与 codemod（如可行） | 跟版后回归 |
| 上游发布节奏 | minor 可独立发布 | 每个上游 minor 跑一次兼容 matrix |

### 8.3 协同节奏
```
上游 minor 发布 ──▶ 下游拉新内核 ──▶ mingdao pack verify ──▶ 绿：跟版
                                              └──▶ 红：上游补兼容层 or 下游适配（记入矩阵）
```

### 8.4 近期具体动作
1. 上游：v0.5.0 出 Pack API v1 + `pack verify`（**下游在等这个才能把工具从 Provider 里搬出来**）；
2. 上游：把本次审计发现的漏计费/缓存失效修掉并在 v0.4.6 发布（下游的费用账本依赖它）；
3. 下游：把 `layer/providers/dify.mjs` 按 Pack 拆分（等 A1–A4 就绪后）；
4. 双方：确定第一个兼容性矩阵版本窗口（建议 0.5.x ↔ deyi 0.2.x）。

## 九、节奏与纪律（防漂移）

1. **每期对照本文**：迭代前先回答「这一期强化的是哪个确定性？有没有撞进『不做』清单？」

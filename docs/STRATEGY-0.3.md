# MingDao-Harness 战略评估（v0.3.0 方向性依据）

> 成文：2026-09-03（v0.2.8 发布后）
> 性质：战略策划，非具体迭代任务。以后按本文件一步步升级迭代；每期迭代前先对照本文件确认方向不漂移。
> 一句话定位：**不做"通用 Agent 平台"，做 DeepSeek 重度用户/中小团队开箱即用的高可用 Coding Agent 终端——DeepSeek 生态里最好用、最能省、最省心的那一个。**

---

## 〇、核心判断：省钱是"果"，好用是"因"

项目里每个省钱手段本质上都在"限制模型自由度"来换取 token：

- 只读阶段只发只读工具 → 写意图需多绕一轮
- 工具 schema 剥描述 → 省输入，但模型参数记忆压力变大
- 步数上限 24 → 复杂任务到点就停
- 滞回压缩 → 早期细节变摘要，可能丢关键约束

**一旦这些手段让任务做不成、做不对、做一半，省的就不是钱，是用户的信任。** 实证：v0.2.7→v0.2.8 修的"跑满 24 步静默收尾"——文件明明写完了，用户看到"没有总结"，体验等于失败。

**因此迭代顺序必须倒过来定：好用托底 → 省钱做乘数 → 省心护城河。绝不允许省钱手段以牺牲任务成功率/多轮灵活性为代价。**

---

## 一、现状根因诊断

### 1.1 真正值钱的东西（护城河材料，已实证）

| 材料 | 证据 | 定位 |
|---|---|---|
| 零依赖 | `src/` 39 文件 ~8.8K 行纯 Node 内置 API；装完即用无 node_modules | 真·稀缺；安装/分发/审计成本全降 |
| DeepSeek 省钱纵深 | 官方词表 BPE tokenizer（黄金值精确命中）· 缓存命中 1/30 计价 · 峰谷双窗口 · Batch 半价 · 前缀两态冻结 · 滞回压缩 | 同类（含大厂 CLI）没有做到这条链的闭环 |
| 工程质量闭环 | strict 棘轮 0/0 · coverage 60% · bench 194 断言 · 三平台 CI · release-checklist 自检 · 打包冒烟 · 桌面签名公证 | "省心"的真护城河 |
| 双界面 + IDE + 同步 | TUI / WebUI(PWA) / VS Code / JetBrains / 桌面 / 云同步 / 36 技能 / MCP | 好用面的广度已够 |

### 1.2 真实短板（按严重度）

**好用线（最痛，决定"能不能打"）：**
1. **能力天花板 = 24 步单回合**：无任务级计划/检查点/续跑，复杂任务（大 repo 迁移、多文件重构、长时任务）到点即断——"能打"的最大瓶颈。
2. **长会话上下文整传**：prompt 成本随对话线性涨；压缩靠"丢细节换摘要"；大 repo 场景很快撑爆预算。
3. **项目理解靠 grep/glob 硬扫**：无语义检索/增量索引，长代码库理解成本高、命中率低。
4. **工具面偏窄**：只读集仅 read/ls/glob/grep/skill；缺 git 只读分析、HTTP 只读抓取、文档检索——真实 Coding 任务抓取面不够。
5. **新会话失忆**：换会话/换项目 = 重来；无跨会话项目记忆。
6. **非 Linux 沙箱空缺**：Windows/macOS 用户多数时间裸跑（ask 兜底，但缺"auto+沙箱"这档）。

**省钱线（方向对，但"省"还没被看见）：**
7. 省钱证据链未外化：用户看不到"这单省了多少 token、缓存命中率贡献"→ 缺钱的可视化归因。
8. 路由分类器样本仅 100+ 条；路由错误 = 隐性浪费且用户无感。

**省心线（相对最好，仍有一刀）：**
9. Node 版本兼容面信用：自评实测 smoke 在 Node 20.15.1 尾部崩溃（全项目零 WASM → 判定环境问题），但项目声明"≥18.17"必须真守得住。
10. 诊断靠手动翻 `~/.mingdao/logs`，无"一键诊断包"。

**工程卫生（小事但真实）：** `browse-x/` 未忽略入库的杂目录；`app.js` 仍 ~1000 行单体（v0.2.8 已拆出 util/constants，可继续渐进拆分，但非护城河、低优先）。

## 二、差异化定位

- 对标物**不是** Claude Code / Codex 的功能全集，而是「用户打开它：DeepSeek 的钱花得明白、任务做得完、装完不操心」。
- 差异化 = **DeepSeek 垂直切面比谁深 × 工程可信度比谁稳**。
- 护城河三根桩：**零依赖（分发端）× DeepSeek 成本经济学（省钱端）× 工程质量闭环（信任端）**。

### 避坑提醒（已认真考虑）
- ❌ 不扩成"全模型省钱平台"（其他模型省钱是伪命题，那是 LiteLLM 赛道）。
- ❌ 不做 React/框架化 UI 重构（有收益但非护城河，且违背零构建；v0.2.8 原生 ESM 拆分已够）。
- ❌ 不因"SQLite 内置查询"强上 SQLite（需 Node ≥22.5，破坏 18/20 兼容矩阵，v0.2.8 已确认，忍住）。

## 三、纵深路线（三线 + 一层底）

### 线 1｜好用 = 能打：Harness 实际能力纵深
1. **任务级长程执行**："24 步单回合" → 「任务意图 → 计划/检查点 → 子任务编排 → 中断可续」；允许任务跨会话续跑、多轮保持上下文焦点。这是"能打"的地基。
2. **项目理解升级**：零依赖语义检索（内存向量 + 余弦/哈希相似度），read/grep 从 O(全扫) 降到 O(相关)。
3. **上下文增量**：滞回压缩之上再做请求侧增量（只回传变化段，不做整段历史重放）。
4. **工具面扩到 Coding 真实场景**：git 只读分析（diff/log/status）、HTTP 只读抓取（SSRF 白名单兜底）、文档结构化检索。
5. **WebUI 做"完成任务的舒服工作台"**：任务过程可回放、结论可复现、交付物可跳转。

### 线 2｜省钱 = 极限 Token 经济学
6. **省钱基准（度量尺，最重要）**：同一任务集下对比 MingDao vs 裸 DeepSeek API vs 对标 CLI，比 token/费用/成功率。护城河用数字证明。
7. **钱的可视化归因**：从"今日 ¥x"→"这一单省多少/花在哪一步/缓存命中贡献"，让用户看见省钱。
8. **推理 token 治理深化**：reasoning effort 按任务复杂度自适应（v0.2.8 已做按模型独立 → 下一步按任务）；简单任务默认关思考。
9. **路由与压缩前置预算**：分类器样本集扩到数百条，路由/压缩的隐性浪费纳入基准。

### 线 3｜省心 = 开箱即用、出事能查
10. **一键诊断包**：`mingdao diagnose` → 自动打包 logs + audit + config（脱敏）+ 版本/平台/Node 信息，贴给反馈即查。
11. **兼容面信用**："Node ≥18.17" 变成 CI 真跑 18/20/22 三版本全绿的硬门禁。
12. 桌面/安装/更新链路已极成熟，保持即可，不返工。

### 底层｜护城河沉淀
13. **公开省钱基准 + 工程质量故事**：把"零依赖 + 194 断言 + 棘轮归零 + 打包冒烟 + 三平台"写成可被第三方验证的工程叙事。
14. 零依赖保持"单一 `node src/cli.js` 即跑"的纯净；任何新能力先问：能否用 Node 内置实现？不能则不进核心。

---

## 四、明确不做（防漂移清单）

- ❌ 全模型省钱平台（LiteLLM 赛道）
- ❌ React/框架化 UI 重构、SQLite 强上
- ❌ 云 SaaS / 托管平台化（保持自建优先、用户掌控）
- ❌ 与主流大厂拼模型能力、拼插件市场广度
- ✅ 保持：零依赖、零构建、DeepSeek 为中心、自建优先

---

## 五、终极目标与一句话承诺

> **"同一件事，MingDao 比直接调 DeepSeek API 省 X%，且任务做得到底。"**

这句话一旦被**公开、可复现的省钱基准**坐实，就是护城河本身：
零依赖 → 易分发；工程闭环 → 可信；省钱基准 → 被看见。
**一切迭代都围绕把这句话做得更硬。**

---

## 六、迭代落地顺序原则

1. **先定「省钱基准任务集」**（这句话的度量尺，决定后面一切数字）。
2. **再排 v0.3.0 主线**：长程执行 vs 语义检索 vs 上下文增量——三者共享"记忆/上下文"地基，先做统一设计再分步实现。
3. **穿插省心小迭代**：诊断包 / CI Node 版本硬门禁 / 省钱仪表盘。
4. 每期迭代发布前对照本文件：新功能是否服务于「好用、省钱、省心」三词之一？是否引入与定位冲突的漂移？——是则调整，否则不做。

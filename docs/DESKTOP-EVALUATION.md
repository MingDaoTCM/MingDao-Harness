# 桌面应用评估（Electron / Tauri / PWA / 其他）

> 目的：回答「要不要做桌面应用、怎么做」。结论先行：**当前不立项，PWA 继续作为默认形态**；触发条件满足后再做，优先 Tauri（体积）或 Electron（复用 Node 核心）。

## 一、现状盘点

MingDao 已有三种运行形态：

| 形态 | 状态 | 体验 |
| --- | --- | --- |
| TUI（mingdao） | ✅ 已交付 | 终端原生，适合老手 |
| WebUI（mingdao web） | ✅ 已交付 | 浏览器全功能 |
| PWA（安装到桌面） | ✅ 已交付 | 独立窗口、桌面图标、离线首页，**已覆盖桌面应用约 80% 体验** |
| VS Code 侧边栏 | ✅ 已交付 | IDE 内嵌，覆盖开发场景 |

参考对象 Hermes Agent CN Desktop 的典型体验：独立窗口、系统托盘、开机自启、自动更新、全局快捷键。PWA 已有独立窗口；缺口集中在**托盘/自启/自动更新/系统集成**四项。

## 二、方案对比

| 维度 | Electron | Tauri 2 | PWA（现状） | 中性化包装（Tauri 替代） |
| --- | --- | --- | --- | --- |
| 打包体积 | ~80–120MB | ~8–15MB | 0（浏览器） | ~10MB |
| 内存占用 | 高（独立 Chromium） | 低（系统 WebView） | 共享浏览器 | 低 |
| 复用现有代码 | **高**：直接把 Node 核心（server.js 全家）搬进主进程，前端 index.html 原样内嵌 | 中：需 Rust 外壳 + sidecar 运行 Node 核心，或前端静态化改造 | 已复用 | 中 |
| 开发成本（单人） | 2–3 周（打包/签名/更新器） | 3–4 周（Rust 学习曲线 + 签名/更新） | 已投入完成 | 2 周 |
| 系统托盘/自启/全局快捷键 | 成熟生态（electron-builder 等） | 支持（tauri 插件） | 无（Chrome 限制） | 支持 |
| 自动更新 | electron-updater 成熟 | tauri updater 可用 | 无需 | 可自建 |
| 跨平台签名 | 需三家证书（Win/mac 付费，Linux 免费） | 同左 | 无需 | 同左 |
| 零依赖哲学 | 冲突（重依赖+构建链） | 冲突（Rust 工具链） | 完全契合 | 冲突 |

## 三、结论与建议

1. **现在不做桌面应用**。PWA 已覆盖核心体验，继续投入的边际收益低；优先把开发资源放在功能深度（如 MCP 生态工具、自动化工作流）。
2. **触发条件**（满足任一即立项）：
   - 用户明确需要**系统托盘常驻 + 开机自启**（如后台任务面板的桌面通知）；
   - 需要**离线安装包分发**（不依赖用户装 Node/browser 的交付场景，如企业内网）；
   - 计划上架应用商店（微软商店/App Store 需原生壳）。
3. **立项时的技术选型**：
   - **首选 Tauri 2**：体积小、内存省，前端可原样复用 `src/web/index.html`；Node 核心以 sidecar 方式运行 `mingdao web`（或后续把核心做成纯 HTTP 服务复用）；成本主要是 Rust 学习与打包签名。
   - 若团队无 Rust 能力且追求最快复用，选 **Electron**：主进程直接 `require` 我们的 Node 模块（零改造），但接受体积与内存代价。
   - 两者都需要：跨平台签名证书预算、自动更新策略、崩溃上报。

## 四、若现在就要「双击即用」的过渡方案（零成本）

- Windows：`start-mingdao.bat`（启动 `mingdao web` 并打开浏览器，最小化窗口）；可发送到桌面快捷方式。
- Linux：`mingdao-web.desktop` 文件（`Exec=mingdao web && xdg-open http://127.0.0.1:3820`），支持桌面图标与开机自启（~/.config/autostart）。

以上方案已在仓库 `install.bat` / 安装文档的思路上可扩展；需要时半天即可补齐并随版本发布。
